Hazards
-------

RAW
===
* sto followed immediately by a ld to the same cache line (64B); quite common

* Yes, without fwd-ing the IPC might get hit bad, but fwd-ing only works if
  the data being read is a subset of that being written; else there must anyways
  be an SRAM read, a struct haz. The ROI of this feels poor...

Some strategies:

1. stall with (MEM3.addr == MEM2.addr and MEM3.w_en and MEM2.r_en). Potentially
   bad IPC; don't know about the stats of cases where the cache line is accessed
   consecutively

2. fwd the whole 512b cache-line and mux it with data_sram's r_data. But dcu2 changes
   in the same cycle; which means I would need to latch the data; wait, do sram macros
   have internal ffs to latch the data, aka must I hold the w_data stable for the entire
   cycle while the write is happening?

Stale-tag/dirty
===============

# Assume I2 arrived before I1

* I1 is supposed to hit,  I2 misses and evicts, and I1's way is the victim, I1 reads stale hit in MEM2
  (stale tag)

* I1 is supposed to miss, I2 is a write-miss or even a write-hit, I1 has no clue of the dirty bit when it
  reaches MEM2; overwrites I2's fetched/written data
  (dirty is 0 for I1 while 1 in reality)

>> Stall MEM1 if MEM2 misses, until the fill/evict is complete. Minimal hardware
   cost, and the extra 1 cycle latency is manageable given how misses are rare, and fill/evict
   latency dominates (main reason...). The only caveat is when there is a tlb miss in MEM1; then, a ptw-walk
   which could have been parallelized is turned serial.

>> In the future, I'm hoping to add store buffs and eventually move on to non-blocking caches.



Flushing
========

Since we only have a single core, and isn't ooo, AND since we have ASIDs, the only actual case
where data needs flushing would be in a JIT case; code in the dcache must move to the icache to
exec.

Which is rare, so I can either:

(i) Remove the data from the cache after eviction

(ii) RMW to preserve valid=1 and tag (2 cycle latency added to the eviction latency; compare this
with evicts to say the L2 cache and if this extra latency is absorbed or if eviction isn't slow
enough to absorb it)

2. PWC
------

Two choices that I had were:

(a) Add a small 4/8-entry CAM just for superpages (Giga or even Mega); which means I cut PPN read
latency by 66%. But the final one is still a RAM (or L2) read.

(b) Either keep the CAM or maybe it to a set-assoc cache of say 16/32 entries and store the pte entries
    too. But mixing superpages and normal pages in set-assoc is hard, so I would've either go fully
    assoc (at which point I waste space on a mask (for the required VPN)) or instantiate set assoc for
    norm and fully assoc for super and parallely query them and mux the hits. Adds significant logic
    and area to the module.

Either choice adds a small invalidation cost to the ptw on fence (which can run parallely unless another
ptw request appears). "Invalidation" because there is nothing to WB.

Plus, the coherence issue lingers, and flushes are expensive; costs as many cycles as there are ways in
our dcache.



The main issue that PTW-to-DCache solves is of course coherence, at the cost of D&V complexity. Unsure
about the gate/routing complexity, but we'll see that shortly.
