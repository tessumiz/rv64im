1. Store valid and dirty in the tag

Do not add write masks. The only cases which write-masks facilitate is when dirty has to change
from 0 to 1, which could be done with RMW. Setting a new tag after a fill can have the valid and
dirty bits hardwired to 10 respectively. Since we only have a single core, and isn't ooo, AND since
we have ASIDs, the only actual case where data needs flushing would be in a JIT case; code in the
dcache must move to the icache to exec.
Which is rare, so I can either:

(i) Write valid, dirty as 00 and tag as garbage (which means flushing removes the data from the
cache itself after eviction, aka assumes you wouldn't be needing it)

(ii) RMW to preserve valid=1 and tag (2 cycle latency added to the eviction latency; compare this
with evicts to say the L2 cache and if this extra latency is negligible)

The only edge case I think I need to bother about is I2<w, hit, !dirty> and I1<going to miss,
victim unfortunately gets chosen as I2's, at which point I suppose I need a comparator between
mem2 and mem3 to get the new dirty value; new_dirty = old_dirty || (victim_matches && mem3.dirty)


2.
Use DFFs. Fear of routing issues, fear of lavishness (area/cost).

Stage-3
-------

>> if exc is set, flush the previous instrs and handle it in this stage

>> track pending reqs with an ff. If this is unset, take an irq, else wait till the op
   completes and only take the irq on the next instr.

>> exc/irq must gate to the cache so it can ignore the req

>> dcache is only going to have [in: valid, out: ready], no "busy" sig.

>> else, read-hit happens here. On miss, fills while stalling the prev pipes. dmem read doesn't
   happen in MEM2 because of routing congestion and synth issues.

>> evict/fills will use moore machines directly from dcu2; since they connect to the miu.
   NOTE: the dirty ff is present in this stage, as the prev ones don't need it at all.

>> on a fault here, updates dcu2's exc and unsets pending_req and asserts stall for one more
   cycle. In the next posedge, the exc is processed.

>> regardless of hit or miss, the last norm write will have stall de-asserted (if no RAW);
   for hits, this happens at the posedge right after reaching stage-3

>> update the plru; fwd-ing isn't worth it. This means plru victim sel *can* lag by 1 if the
   least recently used elm is accessed by I2; I1's victim stays the same then. This is just
   too rare to warrant fwd-ing.



Hazards
-------

RAW
===
* sto followed immediately by a ld to the same cache line (64B); quite common

* stall with (MEM3.addr == MEM2.addr and MEM3.w_en and MEM2.r_en)

* Yes, without fwd-ing the IPC might get hit bad, but fwd-ing only works if
  the data being read is a subset of that being written; else there must anyways
  be an SRAM read, a struct haz. The ROI of this feels poor...



Ld-use
======
* ld res needed in EX; common
* EX to ID is already present

>> 2 cycle penalty; fwd from dcu2 in MEM3 to EX's mux.


Stale-tag/dirty
===============

# Assume I2 arrived before I1

* I1 is supposed to hit,  I2 misses and evicts, and I1's way is the victim, I1 reads stale hit in MEM2
  (stale tag)

* I1 is supposed to miss, I2 is a write-miss or even a write-hit, I1 has no clue of the dirty bit when it
  reaches MEM2; overwrites I2's fetched/written data
  (dirty is 0 for I1 while 1 in reality)

>> Stall MEM1 if MEM2 misses, until the fill/evict is complete. Minimal hardware
   cost, and the extra 1 cycle latency is manageable given how misses are rare, and fill/evict
   latency dominates (main reason...). The only caveat is when there is a tlb miss in MEM1; then, a ptw-walk
   which could have been parallelized is turned serial.
