Stage-1
-------

>> (offset, valid) is fwd-ed from EX to dcache, while the latched
   ones go to the tlb (not planning to keep the ff inside the tlb since
   I might reuse the same tlb for IFU too at which point PC is implicitly
   the input latch ff)

>> the dcache reads the sram data, while the tlb translates addr,
   iff valid is set (valid => .valid && !.exc.valid)

>> tlb misses are handled here; stall for ex and flush for dcu1

>> dcu1 ff <= ppn, vpn, offset, w_en, valid, all tag ways for the set,
              wdata, wmask, exc, ... (pc, wb, csr, all of those)

>> ptw fetches can be aborted with a signal


Crit (potential)
================

This is for the tlb:

Tcq + T(ff-read) + Tcmp + T(way-mux) + T(norm/super mux) + Tsu (dcu1) ;  ff-read meaning Tcq + associated comb
                 |_  superpage cam  _| ;  happens in parallel


Stage-2
-------

>> cache tag cmp, tlb fault check

>> set, way, valid, w_en gets fwd to next stage's data_mem
   (reduces ld use haz penalty from 3 to 2).

   The compiler can't confidently reorder independent instrs before the mem op
   since I lack an ROB while also needing precise exceptions

>> Writes will only happen at the posedge right after stage-3; write-masking forms a
   crit path otherwise. Besides, the only hazard is RAW, which is uncommon; I'm just
   going to stall for this. I'm going to have an address cmp between dcu1 and
   dcu2 which asserts stall on stage-2

>> exc from the previous stage (ptw access fault; note that the ptw isn't
   going to raise page fault, that's the tlb's job) is passed down, or the new
   exc from tlb page fault is passed

>> the plru calcs the victim way.

### Judge the ROI of miss after hit causing perf issues over moving the plru to stage 1
    (lesser congestion, at the cost of an extra delayed cycle of plru update rsp reflected
    in the next victim sel plus 3 extra ffs in dcu1).

>> dcu2 ff <= ppn, vpn, offset, w_en, valid, hit, hit-way, victim-way,
              wdata, wmask, exc, ...


Crit
====
Tcq(dcu1) + 22-bit cmp (6-depth) + way mux (3-depth for 8-way) + Tsu(dcu2) ;  dcu2 ff path
                                 |
                                 |_ hit sig (3-depth redn-OR)  + [valid && !exc && !irq && !pg_fault && hit]
                                    (3-4 depth) + Tsu(r_en) ;  read-hit fwd path


Stage-3
-------

>> if exc is set, flush the previous instrs and handle it in this stage

>> track pending reqs with an ff. If this is unset, take an irq, else wait till the op
   completes and only take the irq on the next instr.

>> exc/irq must gate to the cache so it can ignore the req

>> dcache is only going to have [in: valid, out: ready], no "busy" sig.

>> else, read-hit happens here. On miss, fills while stalling the prev pipes. dmem read doesn't
   happen in MEM2 because of routing congestion and synth issues.

>> evict/fills will use moore machines directly from dcu2; since they connect to the miu

>> on a fault here, updates dcu2's exc and unsets pending_req and asserts stall for one more
   cycle. In the next posedge, the exc is processed.

>> regardless of hit or miss, the last norm write will have stall de-asserted (if no RAW);
   for hits, this happens at the posedge right after reaching stage-3

>> update the plru; fwd-ing isn't worth it.


Paths:
======

T(dmem-read) + T(read-mask comb) + T(EX-fwd-mux + routing delay) + 
T(EX-fwd cmp) ___________________|

T(write-mask comb) + Tsu(dmem-write)

Hazards
-------

RAW
===
* sto followed immediately by a ld to the same cache line (64B); quite common

* stall with (MEM3.addr == MEM2.addr and MEM3.w_en and MEM2.r_en)

* Yes, without fwd-ing the IPC might get hit bad, but fwd-ing only works if
  the data being read is a subset of that being written; else there must anyways
  be an SRAM read, a struct haz. The ROI of this feels poor...



Ld-use
======
* ld res needed in EX; common
* EX to ID is already present

>> 2 cycle penalty; fwd from dcu2 in MEM3 to EX's mux.


Stale-tag
=========

# Assume I2 arrived before I1

* I1 is supposed to hit,  I2 misses, and I1's way is the victim, I1 reads stale hit in MEM2
* I1 is supposed to miss, I2 is a write-miss, I1 has no clue of the dirty bit when it reaches
  MEM2; overwrites I2's fetched data

>> Stall MEM1 if MEM2 misses, until the fill/evict is complete. Minimal hardware
   cost, and the extra 1 cycle latency is manageable given how misses are rare, and fill/evict
   latency dominates. The only caveat is when there is a tlb miss in MEM1; then, a ptw walk which
   could have been parallelized is turned serial.

>> In the future, I'm hoping to add store buffs and eventually move on to non-blocking caches.
